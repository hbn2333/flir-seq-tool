# 版本维护流程

## 基本概念

- Git 提交（commit）：一次可追溯的修改快照，包含具体改动和说明。
- 分支（branch）：隔离某一项修复或功能开发，例如 `codex/fix-transform-layout`。
- 问题记录（issue）：描述现象、复现方式、预期行为和验收标准；本地先使用 `KNOWN_ISSUES.md`，GitHub 建好后可关联到在线 issue。
- 拉取请求（PR）：合并前集中查看改动、测试和复核结果，不是上传数据文件。
- 标签（tag）：为某个确定的提交命名，例如 `v0.1.0`；发布后不随意移动它。
- 发布说明（release notes）：说明这一版增加什么、修复什么、如何验证以及仍有哪些限制。

## 当前仓库边界

原始 `raw`、厂商 `SDK`、本地 `picture`、输出 `clips`、配置 `selections` 不作为默认发布内容。忽略规则不影响本地使用，也不自动移除历史中已跟踪的文件；首次推送前还需核对待发布文件及历史范围。

## 每个版本的工作顺序

1. 选定一个问题或一组紧密相关的问题，写清验收标准。
2. 从稳定基线创建修复分支，先补能复现问题的失败测试。
3. 做最小修复，运行针对性测试和完整回归，检查差异。
4. 在装有 FileSDK 的本机，用最小真实 SEQ 做只读集成验证；大文件交互由人工验收。
5. 复核后合并，更新问题状态及 `CHANGELOG.md`。
6. 对确定的提交打版本标签，推送代码与该标签，并写发布说明。

不要将本地 SDK 和实验数据上传来让云端测试通过。当前测试依赖官方 SDK，部分集成测试依赖本地真实 SEQ；GitHub 自动测试环境需要另行设计，不能直接假设普通云端 runner 能运行全部测试。

## 建议版本顺序（尚未发布）

- `v0.1.0`：保存当前可运行初版和已知问题，作为后续比较基线。
- `v0.1.1`：优先修复编辑模式布局遮挡。
- 后续功能版本：分别加入配置选择/另存，以及子 SEQ 配套 selection；具体版本号在功能范围确认后确定。

已发布版本不通过强制推送改写历史。发现问题时新增修复提交或修复版本；需要撤销代码时优先使用可审查的反向提交，避免破坏已有工作。
