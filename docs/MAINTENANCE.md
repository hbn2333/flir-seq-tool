# 版本维护流程

## 基本概念

- Git 提交（commit）：一次可追溯的修改快照，包含具体改动和说明。
- 分支（branch）：隔离一组修复或功能开发，例如 `codex/fix-viewer-workflow`。
- 问题记录（issue）：描述现象、复现方式、预期行为和验收标准；本地使用 `KNOWN_ISSUES.md`，需要时可关联 GitHub issue。
- 拉取请求（PR）：合并前集中查看改动、测试和复核结果，不是上传实验数据。
- 标签（tag）：为确定的提交命名，例如 `v0.1.0`；发布后不随意移动。
- 发布说明：说明本版改变了什么、如何验证及仍有哪些限制。Git push 成功不等于创建了 GitHub Release。

## 每个版本的工作顺序

1. 选定一个问题或一组紧密相关的问题，写清验收标准。
2. 从稳定基线建立修复分支，先补能复现问题的失败测试。
3. 做最小修复，运行针对性测试和完整回归，检查差异。
4. 在装有 FileSDK 的本机，用最小真实 SEQ 做只读集成验证；原生界面和大文件交互由人工验收。
5. 用户确认后决定合并方式，更新问题状态及 `CHANGELOG.md`。
6. 对确定的提交打新版本标签，明确授权后推送代码和标签，再决定是否创建 GitHub Release。

日常用 `git status` 看所在分支和未提交修改，用 `git diff` 查看未暂存内容，用 `git diff --cached` 检查即将提交的内容。提交前运行测试；提交后用 `git log --oneline` 看历史。`git push` 只在明确决定同步时执行，本轮不自动代做。

不要将本地 SDK 和实验数据上传来让云端测试通过。当前测试依赖官方 SDK，集成测试还依赖本地真实 SEQ；GitHub 自动测试环境需另行设计，不能假设普通云端 runner 能运行全部测试。

## 本地环境与恢复材料

验证使用装有官方 SDK 的独立 Python 3.13.5。若 `python` 指向 Anaconda 而报 `No module named flir_seq_tool`，先运行 `python -c "import sys; print(sys.executable)"` 核对解释器，再使用正确环境。

本轮完整命令为 `python -m pytest -q -rs -p no:cacheprovider`。关闭 pytest 缓存插件可避开当前本机缓存目录权限告警，不跳过测试；具体结果见 [已知问题及验收记录](KNOWN_ISSUES.md)。

配套导出的 pending/recovery 文件属于故障恢复材料，不是普通缓存。不要批量删除或只删标记消除警告；先核对 F1 详情、正式文件/临时文件身份和错误信息，再制定恢复步骤。程序不会执行 journal 中记录的任意恢复路径。
